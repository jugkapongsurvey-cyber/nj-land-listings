## 5. ⛔ สิ่งที่ทดสอบไม่ได้ด้วยเครื่องมือที่มี

### 5.1 Safari และ Mobile Safari

เครื่องที่พัฒนามีแต่เบราว์เซอร์ตระกูล Chromium (Chrome / Edge ใช้เครื่องยนต์เดียวกัน)
**จึงยืนยันได้เฉพาะ Chrome · Edge · Chrome บนมือถือ**

⚠️ **ไม่ได้ทดสอบ Safari / Mobile Safari เลย** — จุดที่มีความเสี่ยงสูงสุดถ้าต่างกัน:

| จุด | ใช้อะไร | ที่ต้องดูบน Safari |
|---|---|---|
| ช่องกรอกในฟอร์ม | `font-size:16px` | แตะแล้วหน้าซูมเองไหม |
| แถบติดต่อติดหนึบ | `position:fixed` + `env(safe-area-inset-bottom)` | ทับแถบล่างของ Safari ไหม |
| แผงตัวกรองจอเล็ก | `position:fixed` + `100dvh` | ความสูงเพี้ยนตอนแถบ URL ย่อ/ขยายไหม |
| รูป hero | `<picture>` + WebP | โหลดรูปถูกขนาดไหม (Safari 14+ รองรับ WebP) |
| แชท/ลิ้นชัก | `overflow:hidden` บน `<html>` | เลื่อนทะลุพื้นหลังไหม |
| `<dialog>` | คอมโพเนนต์ Modal กลาง | Safari 15.4+ เท่านั้น |

**ต้องให้คนที่มี iPhone เปิดเช็ค 6 จุดนี้ก่อนขึ้นจริง** — ใช้เวลาไม่เกิน 10 นาที

### 5.2 Staging

⚠️ **ตอนนี้ยังไม่มี staging environment เลย มีแต่ production เดียว**
ข้อกำหนดระบุว่า "Deploy Staging ก่อน" ซึ่งทำไม่ได้ในสถาปัตยกรรมปัจจุบัน

ทางเลือกที่เป็นไปได้ (**ต้องให้เจ้าของเลือก**):

1. **สร้าง repo ที่สองสำหรับ staging** — คัดลอกเนื้อไปเปิด GitHub Pages อีกชุด
   ที่ `staging.njteedinsure.com` · ตรงกับข้อกำหนดที่สุด แต่ต้องดูแลสองที่
   และต้องกัน `noindex` ทั้งเว็บ ไม่งั้นแข่งอันดับกับของจริง
2. **ใช้ Cloudflare Pages / Netlify ต่อกับ repo เดิม** — ได้ preview URL อัตโนมัติต่อ PR
   · ได้ staging ฟรีต่อทุก PR แต่ต้องย้าย hosting หรือรันคู่กัน
3. **ยอมรับว่าทดสอบบน localhost แล้ว merge ตรง** — คือสิ่งที่ทำอยู่ทุกวันนี้
   · เร็วที่สุด แต่ไม่มีที่ให้เจ้าของกดดูก่อนของจริง

ข้อ 2 น่าจะคุ้มที่สุด เพราะได้ preview ต่อ PR โดยไม่ต้องดูแล repo ที่สอง

### 5.3 Core Web Vitals จริง

วัดจาก `python -m http.server` บนเครื่อง ซึ่ง**ไม่มีการบีบอัดและไม่มีความหน่วงเครือข่าย**
· ตัวเลข LCP / INP / CLS จริงต้องวัดบน production หลัง deploy

## 6. รายการที่ยังค้างอยู่ก่อนขึ้นจริง

### 6.1 ⛔ ของเสียที่อยู่บนเว็บจริงตอนนี้

| เรื่อง | ผลกระทบ | ใครแก้ |
|---|---|---|
| `POST /api/public/partner-apply` ตอบ **404** ขณะที่ `partner-apply.html` ออนไลน์อยู่ | **ผู้สมัครพันธมิตรกดส่งแล้วไม่สำเร็จทุกราย** | merge PR ฝั่งระบบที่ค้างอยู่ |
| รูปประกาศ 458 KB/ใบ ลงช่อง 390×160 | หน้ารวมประกาศโหลด ~10 MB | เลือกทางแก้ (ดู `PERFORMANCE_BEFORE_AFTER.md`) |

### 6.2 ข้อมูลที่ต้องให้บริษัทเติม

- กล่องเหลืองใน `privacy.html` / `terms.html` — ที่อยู่จดทะเบียน · เลขทะเบียนนิติบุคคล ·
  ช่องทางรับคำขอใช้สิทธิ์ PDPA · ระยะเวลาเก็บข้อมูลที่อนุมัติแล้ว
- กล่องเหลืองใน `guides.html` — ชื่อผู้ตรวจทานบทความความรู้
- `land.propertyType` **ว่างทั้ง 22 แปลง** → ชื่อหน้าขึ้นว่า "ขายทรัพย์" แทนประเภทจริง
- ให้ที่ปรึกษากฎหมายตรวจข้อความในหน้านโยบายและข้อกำหนด

### 6.3 ลำดับ deploy ที่ห้ามสลับ

> **1. merge + deploy `nj-survey-system` ก่อน → รอ Render ขึ้นเสร็จ → 2. merge ฝั่งเว็บ**

เหตุผล: เว็บยิงเหตุการณ์สถิติ 8 ชนิดที่ระบบยังไม่รู้จัก (ตอบ 400) และส่งช่อง `attrib`
ที่ระบบยังไม่รับ · หน้าเว็บไม่พัง แต่**ข้อมูลหายเงียบ**

### 6.4 หลัง deploy ต้องทำ

1. ส่ง `sitemap.xml` และ `sitemaps/properties.xml` เข้า Google Search Console
2. ทดสอบลิงก์แปลงในไลน์จริง — ต้องขึ้นการ์ดของแปลงนั้น ไม่ใช่การ์ดกลาง
3. วัด PageSpeed Insights บน production
4. ทีมเพิ่ม/ถอนแปลงเมื่อไหร่ → รัน `node build/properties.js` แล้ว commit
   (ยังไม่ได้ตั้งให้รันเองตามเวลา เพราะจะ push เข้า main อัตโนมัติ = deploy โดยไม่ได้ขอ)
